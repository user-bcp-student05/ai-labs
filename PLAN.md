# Plan de corrección

## Alcance y reglas de ejecución

Este plan conserva el historial de los hallazgos `H-API-01` a `H-API-07` de componente `api`. Esta actualización desarrolla únicamente `H-API-01` y `H-API-04`, ambos con estado `Pendiente` en `HALLAZGOS.md`. Las aprobaciones y ejecuciones antiguas se mantienen como evidencia histórica, no como una aprobación nueva. Esta es una actualización de planificación: no se modifica código ni se ejecutan pruebas.

`docs/ENDPOINTS.md` y `docs/TESTING.md` existen. El contrato de partida es el documentado en `docs/ENDPOINTS.md` y comprobado en el código actual. Se preservarán rutas, métodos, formato del header, status y campos de las respuestas salvo el cambio de seguridad explícitamente solicitado por cada hallazgo; cualquier cambio semántico requerido se coordinará y documentará antes de implementarlo. Las decisiones que no fija `docs/GOOD_PRACTICES.md` deben acordarse, no suponerse. Las futuras ejecuciones de pruebas se registrarán en `PLAN.md` y `docs/TESTING.md` con componente e IDs, resultados reales y cobertura; se mantendrá el umbral de 85% del código modificado.

Antes de cambiar código se ampliará `api/tests/test_api.py` con pruebas de caracterización. Se ejecutarán y registrarán sus resultados reales; las pruebas que reproduzcan una vulnerabilidad podrán fallar contra la implementación actual y deberán quedar identificadas como regresiones esperadas, sin declarar resultados no ejecutados. No se modificarán umbrales de cobertura; se buscará al menos 85% de cobertura del código modificado.

Los siguientes apartados son la propuesta vigente para los dos IDs seleccionados. Los apartados históricos `## H-API-01` y `## H-API-04` más abajo se conservan como antecedente y no sustituyen esta propuesta.

## Item: H-API-01 — Token Base64 con secreto embebido

- **Hallazgo de `HALLAZGOS.md`:** `H-API-01`, vulnerabilidad de severidad alta, estado actual `Pendiente`.
- **Problema y evidencia:** `api/app/security.py:10` fija el secreto; `api/app/security.py:14-28` decodifica Base64 y comprueba formato/secreto/expiración, pero no valida firma criptográfica, issuer ni audience. Los endpoints usan esta dependencia para autenticar solicitudes (`api/app/routes.py:25-51`). El contrato actual documenta el header `Authorization` y el token legado en `docs/ENDPOINTS.md`.
- **Cambio propuesto:** después de acordar el contrato con el emisor, sustituir la decodificación casera por una biblioteca JWT mantenida; PyJWT es la opción propuesta porque verifica firma y claims sin implementar criptografía propia. Permitir solo el algoritmo acordado; exigir firma, `exp`, `iss` y `aud`; mapear los claims acordados a `Identity.username` y `Identity.role`; cargar clave, issuer y audience desde configuración de entorno sin secretos reales. Mantener el header `Authorization`, las rutas y las respuestas exitosas actuales, así como el 401 genérico para credenciales inválidas. No aceptar el token Base64 legado como ruta alternativa una vez habilitado JWT. Revisar advisories y fijar una versión de la dependencia antes de añadirla.
- **Coordinación y límites pendientes:** el emisor debe confirmar algoritmo, issuer, audience, nombres y tipos de claims, expiración y mecanismo de entrega/rotación de claves. No se leerá ni modificará código de otros componentes. Hasta recibir ese acuerdo no se implementará JWT ni se afirmará que el hallazgo está resuelto. Tras el acuerdo, actualizar solo la sección `api` de `docs/ENDPOINTS.md` y registrar pruebas/resultados en `docs/TESTING.md`; no cambiar rutas ni formatos de respuesta.
- **Archivos a tocar cuando se autorice la implementación:** `api/app/security.py`; `api/requirements.txt` si la revisión confirma PyJWT como dependencia necesaria; `api/tests/test_api.py`; sección `api` de `docs/ENDPOINTS.md`; evidencias `docs/TESTING.md`, `HALLAZGOS.md` y este `PLAN.md`.
- **Prueba de caracterización antes de tocar código:** en `api/tests/test_api.py`, registrar el comportamiento actual con un token Base64 válido (un endpoint protegido responde con el status y la forma documentados) y con token ausente, malformado, secreto incorrecto y expirado (HTTP 401 y cuerpo genérico). Ejecutar y guardar el resultado antes de editar `security.py` o dependencias. La aceptación del token legado en esta caracterización solo documenta la línea base; no debe quedar como expectativa posterior. Después del acuerdo, escribir pruebas con claves de prueba aisladas para JWT válido y rechazo de firma, algoritmo, expiración, issuer y audience incorrectos, y verificar que se conserva el contrato de éxito de los endpoints.

## Item: H-API-04 — Carga de archivos usa directamente `file.filename`

- **Hallazgo de `HALLAZGOS.md`:** `H-API-04`, vulnerabilidad de severidad alta, estado actual `Pendiente`.
- **Problema y evidencia:** `api/app/requirement_service.py:12-22` usa el nombre recibido para construir la ruta, lee el archivo completo en memoria y lo escribe sin normalización, allowlist ni máximo de bytes. El endpoint que delega en el servicio es `POST /api/requirements` (`api/app/routes.py:57-64`). `docs/ENDPOINTS.md` confirma HTTP 201 y los campos `owner`, `fileName`, `storedAt` y `size`, y advierte que no hay controles de nombre/extensión/tamaño.
- **Cambio propuesto:** antes de implementar, acordar con el responsable de la política de carga (1) extensiones permitidas, (2) tamaño máximo en bytes, (3) estrategia de almacenamiento seguro del nombre y (4) status/cuerpo para cada rechazo. Con esos valores, validar extensión y nombre antes de escribir; normalizar o generar un nombre de almacenamiento seguro; comprobar que la ruta resuelta permanezca dentro del directorio permitido; leer en bloques con un límite más un byte para detectar excesos sin acumular el archivo completo; y evitar archivos parciales ante errores. Usar constantes/configuración con nombre, funciones de responsabilidad única y mensajes genéricos. Mantener HTTP 201 y el esquema de respuesta válido. Conservar la semántica actual de `fileName` y `storedAt` si es compatible con el almacenamiento seguro; si el nombre/ruta almacenados necesariamente cambian, acordar y documentar explícitamente esa variación antes de implementarla. No inventar extensiones, tamaños ni códigos de rechazo.
- **Coordinación y límites pendientes:** `docs/GOOD_PRACTICES.md` prescribe normalizar nombre, restringir extensión y tamaño, pero no fija valores. H-API-04 no se cierra ni se implementa hasta contar con la política acordada. El test de 1 MiB registra una observación y no establece un máximo. No se inspeccionarán ni modificarán otros componentes para determinar la política.
- **Archivos a tocar cuando se autorice la implementación:** `api/app/requirement_service.py`; posiblemente `api/app/routes.py` solo si hace falta mapear errores acordados a respuestas HTTP; `api/tests/test_api.py`; sección `api` de `docs/ENDPOINTS.md` solo si cambia la semántica documentada de `fileName`, `storedAt` o los errores; evidencias `docs/TESTING.md`, `HALLAZGOS.md` y este `PLAN.md`.
- **Prueba de caracterización antes de tocar código:** en `api/tests/test_api.py`, ejecutar y conservar los casos actuales de carga válida (HTTP 201, esquema, `storedAt`, tamaño y bytes), archivo vacío sin extensión, muestra de 1 MiB, multipart malformado (400), campo `file` ausente (422) y autenticación ausente (401). Añadir antes de editar el servicio una caracterización con un nombre ordinario que fije los valores actuales de `fileName` y `storedAt`; si se caracteriza un nombre con separadores, limitar cualquier escritura a `tmp_path` y verificar el comportamiento solo dentro de ese directorio temporal. Después de acordar la política, agregar casos para extensión permitida/no permitida, nombre manipulado, tamaño exactamente en el límite y excedido, status/cuerpo acordados y ausencia de escrituras fuera del directorio o de archivos parciales. No usar la muestra de 1 MiB como límite ni declarar esas pruebas futuras como ejecutadas.

## H-API-01 — Token Base64 con secreto embebido

- **Hallazgo:** `H-API-01`, Vulnerabilidad, severidad alta, estado `Aprobado`.
- **Problema:** `legacy_identity` confía en un token Base64 con secreto fijo y solo revisa formato y expiración (`api/app/main.py:14`, `api/app/main.py:17-26`). No verifica firma JWT, emisor ni audiencia y expone detalles de excepción en el 401.
- **Cambio propuesto:** sustituir la decodificación casera por validación JWT con PyJWT, algoritmo permitido explícitamente, firma y claims `exp`, `iss` y `aud` obligatorios. Obtener clave/configuración de variables de entorno; no incluir secretos de producción. Responder errores de autenticación con mensaje genérico y conservar detalles solo en logging controlado. Fijar una versión de PyJWT después de revisar advisories. La API conservará `Authorization: Bearer ...` y el formato de identidad interno `username`/`role`.
- **Coordinación pendiente:** confirmar con el emisor JWT el algoritmo, `issuer`, `audience`, nombres de claims y suministro/rotación de claves. No leer ni cambiar el código del emisor fuera de `api/`; bloquear la implementación de validación final hasta disponer de este contrato.
- **Archivos a tocar:** `api/app/main.py`; nuevo `api/app/security.py` para validación; `api/requirements.txt`; `api/tests/test_api.py`.
- **Caracterización antes de tocar código:** registrar status, cuerpo y acceso de un endpoint protegido con token legacy válido, expirado, malformado y ausente. Después, añadir pruebas JWT con claves de prueba aisladas para aceptación válida y rechazo de firma, expiración, `issuer` y `audience` inválidos, además de verificar que las respuestas exitosas de los endpoints conservan sus formas. La prueba que describe aceptación legacy documenta el comportamiento anterior; no implica que deba seguir aceptándose tras la migración.

## H-API-02 — Autorización de tareas controlada por `owner` del cliente

- **Hallazgo:** `H-API-02`, Vulnerabilidad, severidad alta, estado `Aprobado`.
- **Problema:** `GET /api/tasks` y `GET /api/summary` permiten escoger `owner`; `POST /api/tasks` también permite asignarlo (`api/app/main.py:68-71`, `api/app/main.py:78-84`, `api/app/main.py:91-94`).
- **Cambio propuesto:** ligar las consultas y altas a `identity["username"]` verificado. Mantener `owner` en query/body para no cambiar el contrato de entrada; cuando se omita o coincida con la identidad, conservar el resultado válido actual. Rechazar con 403 una petición que indique otro propietario y asegurar que no revele ni cree datos de ese usuario. No inferir una política basada en `role` sin un acuerdo explícito.
- **Archivos a tocar:** `api/app/main.py`; `api/tests/test_api.py`; al extraer persistencia, `api/app/repository.py` y `api/app/service.py` (ver `H-API-06`).
- **Caracterización antes de tocar código:** probar listado y resumen sin `owner`, alta sin `owner` y con el mismo `owner`, incluyendo status, orden y forma JSON. Añadir casos de línea base que documenten la lectura/atribución actual con un `owner` distinto; después del cambio, convertirlos en regresiones que esperan 403 y verifican que no se filtran ni se crean tareas para otro propietario.

## H-API-03 — Consultas SQL construidas por concatenación

- **Hallazgo:** `H-API-03`, Vulnerabilidad, severidad alta, estado `Aprobado`.
- **Problema:** valores de filtro y de la tarea se concatenan en SQL en listado, resumen e inserción (`api/app/main.py:70-71`, `api/app/main.py:84-87`, `api/app/main.py:93`).
- **Cambio propuesto:** parametrizar todos los valores con placeholders de `sqlite3`; mantener `ORDER BY id`, defaults, commit y mapeo de respuesta. Parametrizar también el ID recuperado al consultar la fila insertada, aunque provenga de `lastrowid`, para evitar concatenaciones SQL innecesarias.
- **Archivos a tocar:** `api/app/main.py`; `api/tests/test_api.py`; posteriormente `api/app/repository.py` al separar persistencia en `H-API-06`.
- **Caracterización antes de tocar código:** cubrir el orden y forma del listado, el alta válida con sus defaults, y los totales/formato del resumen. Añadir casos de regresión con comillas en título, descripción y filtro `owner`, comprobando que se tratan como valores literales y que no cambian la consulta ni impiden recuperar la tarea.

## H-API-04 — Carga de archivos usa directamente `file.filename`

- **Hallazgo:** `H-API-04`, Vulnerabilidad, severidad alta, estado `Aprobado`.
- **Problema:** se concatena el nombre recibido a la ruta de uploads, se lee el archivo completo en memoria y se escribe sin límite, normalización o allowlist (`api/app/main.py:107-112`).
- **Cambio propuesto:** normalizar el nombre, usar un nombre de almacenamiento seguro/único y verificar que la ruta resuelta permanezca dentro del directorio configurado. Aplicar una allowlist de extensiones y un máximo de bytes mediante constantes con nombre, leyendo en bloques y deteniéndose al superar el máximo para no cargar el archivo entero en memoria. Acordar y documentar las extensiones y el límite exactos antes de codificarlos; `docs/GOOD_PRACTICES.md` no fija esos valores. Definir respuestas de rechazo explícitas para extensión y tamaño. Mantener el status 201 y los campos `owner`, `fileName`, `storedAt` y `size` para cargas válidas; conservar el nombre de cliente en `fileName` sin usarlo como ruta de almacenamiento.
- **Archivos a tocar:** `api/app/main.py`; nuevo `api/app/requirement_service.py` al separar la validación y almacenamiento en `H-API-06`; `api/tests/test_api.py`.
- **Caracterización antes de tocar código:** ampliar la prueba actual para comprobar status 201, campos de respuesta, tamaño y bytes guardados con un nombre normal. Añadir líneas base que documenten el tratamiento actual de extensiones, nombres y tamaños. Una vez acordadas allowlist, límite y statuses de rechazo, probar extensión permitida y denegada, nombre con traversal, límite exacto y exceso; comprobar que los rechazos no escriben fuera del directorio ni almacenan contenido. No fijar valores de extensión/tamaño en las pruebas hasta resolver ese acuerdo.

## H-API-06 — Rutas, persistencia, reglas y serialización concentradas en un archivo

- **Hallazgo:** `H-API-06`, Refactor, severidad baja, estado `Aprobado`.
- **Problema:** `main.py` contiene autenticación, conexión y schema SQLite, SQL, reglas de resumen, serialización, carga y rutas (`api/app/main.py:17-127`).
- **Cambio propuesto:** después de caracterizar y corregir los riesgos anteriores, separar responsabilidades con límites pequeños: `main.py` para crear/configurar la app; `routes.py` para HTTP; `security.py` para identidad; `models.py` para DTOs; `repository.py` para SQLite y consultas; `service.py` para reglas de tareas; `requirement_service.py` para validar/guardar archivos. Cada función realizará una sola tarea, sin duplicar conversiones SQL/JSON ni introducir condicionales profundamente anidados o valores mágicos.
- **Archivos a tocar:** `api/app/main.py`; nuevos `api/app/routes.py`, `api/app/security.py`, `api/app/models.py`, `api/app/repository.py`, `api/app/service.py` y `api/app/requirement_service.py`; `api/tests/test_api.py`.
- **Caracterización antes de tocar código:** completar primero pruebas de listado, alta, resumen, carga, health y autenticación, incluyendo rutas, status, defaults, claves JSON, orden, semillas SQLite, configuración de directorio de subida y cierre de conexión. Ejecutar la suite antes de mover lógica y después de cada extracción para verificar paridad en los flujos válidos y conservar explícitas las regresiones de seguridad previstas.

## H-API-07 — Tipado crudo, excepciones amplias, lógica anidada y duplicación

- **Hallazgo:** `H-API-07`, Refactor, severidad baja, estado `Aprobado`.
- **Problema:** requests y responses se expresan como `dict[str, Any]`, hay capturas generales y errores crudos, el cálculo de `highPriorityOpen` está anidado y se repite la proyección SQL (`api/app/main.py:17-26`, `api/app/main.py:56-68`, `api/app/main.py:70`, `api/app/main.py:78`, `api/app/main.py:87`, `api/app/main.py:91-104`, `api/app/main.py:117-121`).
- **Cambio propuesto:** definir modelos Pydantic de request/response con tipos concretos que conserven nombres, alias (`createdAt`), defaults y formas observadas; caracterizar antes las coerciones actuales y decidir explícitamente cualquier validación que las cambie. Reutilizar un único mapeo/proyección de tarea, mantener SQL en repositorio parametrizado y mover reglas a servicios. Simplificar el conteo con condiciones legibles y retornos tempranos. Sustituir capturas generales por excepciones específicas; preservar la forma de error donde sea contrato observado, pero no devolver texto crudo de excepciones. Dar nombre a las constantes de políticas acordadas.
- **Archivos a tocar:** `api/app/main.py`; nuevos `api/app/models.py`, `api/app/service.py`, `api/app/repository.py` y `api/app/requirement_service.py`; `api/tests/test_api.py`.
- **Caracterización antes de tocar código:** comprobar payloads válidos y límites relevantes, defaults/coerciones actuales de `POST /api/tasks`, campos y alias de cada respuesta, `byStatus`, reglas de `DONE`/`ARCHIVED`, error de token inválido y fallo de health. Usar estas pruebas para preservar formas de éxito; acordar y probar cualquier cambio intencional de coerciones o contenido de error antes de introducirlo.
